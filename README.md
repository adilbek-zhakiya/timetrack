# Учёт рабочего времени

Небольшое веб-приложение для учёта времени сотрудников. Можно добавить сотрудника, запустить и остановить таймер с описанием задачи и посмотреть записи и итог по каждому сотруднику за любой период. Данные хранятся в SQLite и сохраняются после перезапуска.

Стек: Python 3.11, FastAPI, SQLite (стандартный модуль `sqlite3`), страница на HTML, CSS и JavaScript без сборки, тесты на pytest.

Все имена и задачи в демо-данных вымышленные.

## Запуск

```bash
python -m venv venv
venv\Scripts\activate            # Windows
# source venv/bin/activate       # Linux, macOS
pip install -r requirements.txt

python seed.py                   # необязательно: 8 сотрудников и записи за 4 недели
uvicorn app.main:create_app --factory --port 8030
```

Приложение откроется на http://127.0.0.1:8030.

База по умолчанию лежит в `data/timetrack.db` внутри папки проекта. Другой путь задаётся переменной `DB_PATH`. `python seed.py --reset` стирает данные и заполняет базу заново.

Через Docker:

```bash
docker compose up -d --build
docker exec timetrack python seed.py
```

База хранится в томе `timetrack-data`, поэтому `docker compose restart` и пересборка её не стирают.

## Тесты

```bash
pytest -q
```

Каждый тест работает со своей временной базой и с часами, которые тест двигает сам, поэтому результаты не зависят от текущего времени. Что проверяется:

| Сценарий | Тест |
|---|---|
| Добавление сотрудника, пустое имя, дубль с другим регистром | `test_add_employee`, `test_employee_name_required`, `test_duplicate_employee_ignores_case` |
| Запуск и остановка таймера | `test_start_and_stop_timer` |
| **Повторный запуск**, когда таймер уже идёт: ответ 409, первая запись не тронута | `test_repeated_start_is_rejected` |
| Восемь одновременных запусков создают ровно один таймер | `test_parallel_starts_create_one_timer`, `test_running_timer_is_unique_in_database` |
| Новый запуск после остановки | `test_start_again_after_stop` |
| Остановка без таймера и двойная остановка | `test_stop_without_running_timer`, `test_stop_twice` |
| **Пустой отчёт**: без сотрудников и с сотрудниками без записей (нули, а не ошибка) | `test_empty_report_without_employees`, `test_empty_report_lists_employees_with_zero` |
| Итоги по сотрудникам и фильтр по одному сотруднику | `test_report_totals_per_employee`, `test_report_filtered_by_employee` |

| Идущий таймер считается до текущего момента и не попадает в будущие периоды | `test_running_timer_counts_until_now`, `test_running_timer_not_in_future_period` |
| Запись или таймер, начатые за несколько дней до периода, всё равно попадают в отчёт | `test_long_entry_started_days_before_period`, `test_long_running_timer_counts_in_today` |

## Как устроено

```
app/
  db.py         схема и подключение к SQLite
  service.py    сотрудники, таймер, отчёт; вся логика здесь
  main.py       HTTP-маршруты, превращает ошибки сервиса в коды ответа
  static/       страница: index.html, app.js, style.css
tests/          проверки сценариев через HTTP
seed.py         вымышленные данные для демонстрации
```

API:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/employees` | сотрудники и их идущие таймеры |
| POST | `/api/employees` | добавить сотрудника `{"name": "..."}` |
| POST | `/api/employees/{id}/timer/start` | запустить таймер `{"description": "..."}` |
| POST | `/api/employees/{id}/timer/stop` | остановить таймер |
| GET | `/api/report?date_from=&date_to=&tz=&employee_id=` | записи и итоги за период |

Решения, которые стоит знать:

- **Один таймер на сотрудника гарантирует база.** Частичный уникальный индекс `ux_time_entries_running` разрешает только одну запись без `stopped_at` на сотрудника. Проверка в коде «сначала SELECT, потом INSERT» пропустила бы два одновременных запроса, индекс их не пропускает. Повторный запуск возвращает 409 с понятным текстом, автоматически предыдущий таймер не останавливается, чтобы случайный клик не испортил чужую запись.
- **Время хранится в UTC**, а границы периода считаются в часовом поясе браузера (параметр `tz`). Без этого запись, сделанная в 23:30 по Алматы, попала бы в отчёт за следующий день.
- **В итог идёт только часть записи внутри периода.** Запись с 22:00 до 01:00 даёт 2 часа в первый день и 1 час во второй. Сама запись видна в обоих днях.
- **В отчёте есть все сотрудники**, даже без записей. Пустой период показывает нули и сообщение «За этот период записей нет».
- **Поиск записей за период ограничен с двух сторон.** Как и зачем, описано в ошибке 4 ниже.
- Даты «сегодня» и «эта неделя» на странице собираются из местных компонентов даты. `toISOString()` здесь не подходит: она даёт дату в UTC, и вечером по местному времени это уже завтрашний день.
- Если быстро сменить даты отчёта, ответы могут прийти не по порядку. Страница рисует только ответ на последний запрос.
- Путь к базе по умолчанию строится от папки проекта, поэтому запуск сервера из другого каталога не создаёт вторую, пустую базу.
- Текущее время передаётся в сервис параметром, поэтому в тестах его можно подменить.

## Как использовался ИИ

Инструмент: **Claude Code** (приложение для ПК) с моделью **Claude Opus 5.5**. Выбрал агентный режим, потому что модель сама запускает тесты и открывает приложение во встроенном браузере. Так ошибки видны сразу, до того как я начинаю читать код.

Как шла работа:

1. В корне моих проектов лежит файл с правилами для агента (`CLAUDE.md`): как называть окружение, что демо-данные должны быть правдоподобными, что в интерфейсе не должно быть служебных подсказок, что сначала нужно посмотреть, как сделано в соседних проектах. Агент читает его сам, поэтому стек и стиль он взял из моего проекта на FastAPI и SQLite, а не придумывал с нуля.
2. Передал агенту текст задания целиком и спросил про подвохи. Разобрали спорные места: повторный запуск, гонка двух запросов, пустой отчёт, часовые пояса, записи через границу периода, идущий таймер в отчёте. Поведение по каждому описано выше.
3. Агент написал код и тесты, сам запускал pytest и открывал приложение во встроенном браузере, в том числе на телефонной ширине.
4. Я спросил, что будет со скоростью, если данных станет много. Агент собрал отдельную базу на 156 600 записей (50 сотрудников за 2 года), замерил отчёт и по `EXPLAIN QUERY PLAN` нашёл, где теряется время.
5. Интерфейс переделывали дважды. Первый вариант с вкладками и карточками и второй, где всё было на одном экране, оказались перегружены. В итоге остались две простые страницы: список сотрудников с итогом за период и страница сотрудника с таймером и записями.
6. После этого я прочитал код и проверил решения, описанные в разделе «Как устроено».

Каждая ошибка ниже нашлась своим способом: тестом, проверкой в браузере или замером. Без запуска кода ни одну из них не было бы видно.

Примеры запросов (сокращены, смысл тот же):

> Вот тестовое задание целиком. Есть ли в нём подвохи, которые легко пропустить?

> Ошибки в README выглядят выдуманными. Какие из них ты действительно видел при запуске, а какие нет?

> Что будет со скоростью отчёта, если записей станет много? Стоит ли оптимизировать запросы?

> Интерфейс теряет суть задачи. Сделай проще и понятнее.

> Всё равно слишком много на одном экране. Раздели на список сотрудников и отдельную страницу сотрудника.

## Найденные и исправленные ошибки

Все пять ошибок были в коде, который сгенерировала модель.

1. **Дубли сотрудников с кириллицей.** Сначала уникальность имени была сделана через `COLLATE NOCASE`. Тест `test_duplicate_employee_ignores_case` упал: SQLite без расширения ICU приводит к одному регистру только латиницу, и «Айгерим Сапарова» и «айгерим сапарова» считались разными людьми. Исправление: отдельная колонка `name_key` с `name.casefold()` из Python и уникальным индексом. По ней же идёт сортировка, которая до этого для кириллицы тоже зависела от регистра.

2. **Идущие таймеры в будущих периодах.** При проверке в браузере отчёт за следующую неделю показал «0 мин» и четыре записи вместо пустого списка. Условие отбора было `stopped_at IS NULL OR stopped_at > начало_периода`, то есть идущий таймер считался бесконечным и попадал в любой будущий период. Исправление: для идущего таймера концом считается текущий момент, `COALESCE(stopped_at, сейчас) > начало_периода`. Добавлен тест `test_running_timer_not_in_future_period`.

3. **Случайные ошибки 500 при работе с базой.** На странице сотрудника отчёт иногда не открывался, в журнале сервера была ошибка `SQLite objects created in a thread can only be used in that same thread`. FastAPI выполняет зависимость `get_conn`, которая открывает подключение, и сам маршрут в разных потоках из пула. По умолчанию `sqlite3` запрещает передавать подключение между потоками. Когда потоки совпадали, всё работало, поэтому тесты и первые проверки в браузере ошибку не показали. Исправление: `check_same_thread=False`. Это безопасно, потому что подключение живёт один запрос и одновременно двумя потоками не используется. Тест `test_connection_works_from_another_thread` повторяет ситуацию стабильно: без исправления он падает. Заодно страница теперь пишет при ошибке сервера «Не удалось выполнить запрос», а не «Проверьте введённые данные».

4. **Отчёт за свежий период перебирал всю таблицу.** Нашлось замером на базе из 156 600 записей. Отчёт за текущую неделю шёл 128 мс, за неделю двухлетней давности 14 мс. План запроса показал причину: индекс по `started_at` использовался только с одной стороны (`started_at < конец_периода`), и для свежего периода под это условие попадали почти все записи. Ограничить поиск снизу напрямую нельзя: запись, начатая до периода, всё равно должна в него попасть. Индекс по `stopped_at` просто переворачивает проблему: свежие недели становятся быстрыми (1,8 мс), а старые медленными (110 мс). Исправление: ни одна закрытая запись не длиннее самой длинной из закрытых, поэтому поиск начинается с «начало периода минус самая длинная запись». Самую длинную запись даёт индекс по выражению `julianday(stopped_at) - julianday(started_at)` за доли миллисекунды. Идущие таймеры учитываются отдельно: граница сдвигается к самому раннему из них. Код в `_earliest_possible_start` в `service.py`, тесты `test_long_entry_started_days_before_period` и `test_long_running_timer_counts_in_today`.

5. **Первая версия этого исправления сделала отчёт медленнее.** Повторный замер дал 123 мс за текущую неделю и 130 мс за старую. Отдельный замер каждого вспомогательного запроса показал: `MIN(started_at) WHERE stopped_at IS NULL` выполнялся 112 мс. SQLite выбрал для него индекс по `started_at` и шёл от самых старых записей, пока не встретит идущую. Если идущих таймеров нет, он перебирал всю таблицу. Исправление: частичный индекс `ix_time_entries_running_started` только по идущим записям.

Итог на той же базе (весь отчёт целиком, вместе с подсчётом итогов в Python):

| Отчёт | До | После |
|---|---|---|
| Текущая неделя, 50 сотрудников (1 500 записей) | 128 мс | 16 мс |
| Текущая неделя, один сотрудник | 110 мс | 1,3 мс |
| Неделя двухлетней давности | 14 мс | 16 мс |
| Год целиком (78 600 записей) | 860 мс | 890 мс |

Отчёт за год упирается в объём самих данных, индексы тут не помогут. Что с этим делать, описано в разделе «Что улучшить дальше».

## Что улучшить дальше

Сейчас страницы получают все записи за период целиком. Для задания этого хватает, но на большой базе становится заметно. Замер через API на той же базе из 156 600 записей:

| Запрос | Время | Размер ответа | Записей в ответе |
|---|---|---|---|
| Список сотрудников, неделя | 268 мс | 287 КБ | 1 500 |
| Список сотрудников, год | 4,8 с | 15 МБ | 78 600 |
| Один сотрудник, год | 210 мс | 295 КБ | 1 572 |

Список сотрудников показывает только итог по каждому, но загружает все записи, потому что итоги считаются в Python. План:

1. **Итоги считать в SQL.** `/api/report` отдаёт только итог и число записей по сотрудникам. Обрезка записи по границам периода переносится в `GROUP BY`: длительность внутри периода это разница между меньшим из «конец записи» и «конец периода» и большим из «начало записи» и «начало периода». Ответ за любой период весит несколько килобайт.
2. **Записи отдавать частями.** Отдельный `/api/entries` с `offset` и `limit` возвращает 50 записей и их общее число. На странице сотрудника под таблицей появляется «Показано 50 из 1 572» и кнопка «Показать ещё».

Сейчас это не сделано сознательно. В задании нет требований к объёму данных, а без пагинации код заметно проще.
